# Findings

This document records repository-level findings that matter when changing the
application. Resolved items describe the current safeguards, while open items
describe operational constraints rather than customer-facing behavior.

## Resolved safeguards

| Area                     | Current safeguard                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sitemap freshness        | Product mutations revalidate the sitemap tag and relevant public routes.                                                                          |
| WhatsApp return link     | The thank-you page accepts only a valid `https://wa.me/` link.                                                                                    |
| R2 cleanup               | Product image deletion removes unreferenced keys after the database transaction commits. Shared keys survive until their final reference is gone. |
| Note and brand freshness | Related public pages are revalidated after translation or display-name changes.                                                                   |
| Action envelopes         | Admin actions use shared `ActionResult<T>` and `fieldErrors()`. Raw Spanish fields remain at the client boundary.                                 |
| Cart compatibility       | Persisted cart version 2 migrates legacy image fields to the English internal model.                                                              |
| Public action safety     | Checkout uses a honeypot, request validation, price rereads, and rate limiting.                                                                   |
| Product safety           | Publication checks, relationship ID validation, product ownership checks, and R2 key validation run server-side.                                  |

| "Se parece a" invalidation scope | `revalidateStore` in `src/app/admin/(panel)/productos/actions.ts` calls `revalidateTag(TAG_SIMILAR_PRODUCTS, "max")`, which marks the shared cached ranking stale for every product, but only calls `revalidatePath` for the edited product's own `/producto/[slug]` page (and its brand page). Other products whose "Se parece a" list could have shifted are not individually revalidated as pages. | Intentional. Product pages call `getSiteSettings()`, which calls `connection()` in `src/lib/settings.ts`, so they render dynamically and are never served from the cache Next keeps for statically rendered pages. The only staleness is the tagged data cache: with `"max"`, `revalidateTag` uses stale-while-revalidate, so the first request to another product's page after the edit can still recompute from the (now stale-marked) similar-products cache entry while Next revalidates it in the background; the next request gets the refreshed ranking. No page goes permanently stale without a visit, and enumerating every other product's `/producto/[slug]` path on each edit would be expensive for no lasting benefit. |

## Deferred refactoring findings

These were found during a cleanup refactor and deferred because fixing them
changes behavior or touches the price, order, or image-write paths, which have
no automated test coverage.

| Topic                                    | Current behavior                                                                                                                                                                                                                                                                                                                                               | Why it is deferred                                                                                                                                                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order price read outside the transaction | `createOrder` in `src/app/(store)/checkout/actions.ts` reads `ProductVariant` prices with `prisma.productVariant.findMany` before opening `prisma.$transaction`; the transaction only takes the order-number sequence and creates the `Order`/`OrderItem` rows.                                                                                                | A price change between that read and the create still persists the earlier price in the `OrderItem` snapshot. Fixing it touches the price and order-write path.                                                 |
| Duplicated variant revalidation          | `createOrder` reimplements the validation done by `validateCartItems` in `src/lib/store/server-cart.ts` (same select, same map by id, same invalid reasons), because checkout needs `Prisma.Decimal` amounts while `validateCartItems` returns price strings.                                                                                                  | Unifying the two touches the price path.                                                                                                                                                                        |
| In-flight dedup in cart reconciliation   | `useCartReconciliation` (`src/lib/store/use-cart-reconciliation.ts`) keeps a module-level `inFlightValidation` dedup because the presentational `CartItemList` it runs inside (`src/components/store/cart/cart-item-list.tsx`) mounts in both `cart-drawer.tsx` and `carrito/_components/cart-content.tsx`, so it can run twice at once.                       | Removing the dedup changes when the drawer reconciles with the database, a behavior change.                                                                                                                     |
| Duplicated sync algorithm                | `syncVariants` and `syncImages` in `src/app/admin/(panel)/productos/actions.ts` both implement the same algorithm: collect kept IDs, `deleteMany` the rest, then update or create rows by index.                                                                                                                                                               | An off-by-one there corrupts product variants or images, and the image-write path has no automated coverage.                                                                                                    |
| Single-use `react-dropzone`              | `src/app/admin/(panel)/productos/_components/image-panel.tsx` is the only place that imports `react-dropzone`'s `useDropzone`, for accept/maxSize/drag state.                                                                                                                                                                                                  | Low value: it reimplements working UX, and the server already validates upload type and size.                                                                                                                   |
| Per-route Open Graph image files         | Nine `opengraph-image.tsx` files under `src/app/(store)/` (`checkout`, `como-comprar`, `catalogo`, `carrito`, `que-es-un-tester`, `contacto`, `marca/[slug]`, `producto/[slug]`, `pedido/[number]/gracias`) re-export the single image generated in `src/app/(store)/opengraph-image.tsx`, since Next's file convention does not inherit into nested segments. | The failure mode is silent (WhatsApp link previews). `src/lib/seo.ts` also documents intentionally not setting `openGraph.images`, so collapsing the duplication needs a design decision, not a mechanical fix. |
| Eyebrow label typography                 | Small uppercase labels use several font sizes and tracking values.                                                                                                                                                                                                                                                                                             | Normalizing them changes rendered pixels; see `design-system/parfam-mdq/MASTER.md` (finding B-08) for detail.                                                                                                   |

## Presentation-only price arithmetic

Checkout and cart components use `Number()` for display totals in
`src/app/(store)/checkout/_components/checkout-form.tsx`,
`src/components/store/cart/cart-summary.tsx`, and
`src/components/store/cart/cart-item-row.tsx`. This is an intentional
presentation exception to the Decimal rule. Prices still cross to the client
as strings, writing actions reread prices from the database, and persisted
order totals use `Prisma.Decimal` on the server.

## Refactoring constraints

Historical Prisma migrations, Spanish public routes, query keys, raw action
payloads, localStorage keys, R2 prefixes, WhatsApp placeholders, and
environment variables are external or persisted contracts. Keep them stable, or
introduce an explicit migration or adapter.

The code is the authoritative source. Refresh this document whenever an
implementation change invalidates one of these statements.
